# AuthCore Phase 8 — Application / Extension Integration

## Purpose

Phase 8 defines the integration boundary between AuthCore and product plugins. Applications and extensions can register a shared user-management entry point without exposing or selecting an arbitrary AuthCore application ID from the browser.

## Integration API

Application plugins can register the common user-management page with:

```php
AuthCore::registerUserManagementMenu(
    'alumni',
    'alumni-core',
    'Users',
    'AlumniCore Users'
);
```

The parameters are:

1. Application Key
2. WordPress parent menu slug
3. Menu title
4. Page title
5. Optional WordPress capability (default: `manage_options`)

The returned menu slug is generated by AuthCore and is not based on a user-supplied application ID.

## Application context resolution

When an `application` registers the integration, AuthCore resolves its registered Application ID internally.

When an `extension` registers the integration, AuthCore resolves the extension's `parent_application_id` and uses the parent Application as the user-management context.

Therefore:

```text
AlumniCore (application)
    ↓
application_id = 10
    ↓
AuthCore common user management

AlumniVoice (extension)
    ↓
parent = AlumniCore
    ↓
application_id = 10
    ↓
AuthCore common user management
```

AlumniVoice does not receive an independent user namespace.

## Application isolation

The browser does not choose the AuthCore application ID. The registered integration context determines the application ID before the page is rendered.

User retrieval continues to use the AuthCore public API and is therefore scoped to the resolved application context.

## WordPress admin integration

The common page is attached to the product's existing WordPress admin menu using `add_submenu_page()`.

AuthCore does not hardcode AlumniCore, StageArt, CDRMap, or any other product. Each product supplies its own Application Key and parent menu slug.

## Extension behavior

An extension can register the same common user-management page using its own Application Key. AuthCore detects the extension and automatically resolves the parent application.

This keeps the integration contract simple while preserving the rule that extensions share their parent application's identity and permissions.

## Security

- Application IDs are resolved server-side from registered metadata.
- No arbitrary `application_id` query parameter is accepted by the common page.
- The page checks the configured WordPress capability before rendering.
- User data is retrieved through AuthCore's application-scoped API.
- HTML output is escaped.

## Scope

Phase 8 establishes application/extension integration. Full create/edit/delete controls, search, pagination, and richer capability administration remain part of the later UI/acceptance work.

## Runtime verification

The integration code has been committed to the feature branch. A real WordPress runtime test against AlumniCore, StageArt, or CDRMap has not yet been performed.
